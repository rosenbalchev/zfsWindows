# Project: Native ZFS Filesystem Driver for Windows — C + .NET 10 + Automated Integrity and Stress Testing

## Role

You are a senior autonomous software engineering team with expertise in:

- Windows kernel-mode filesystem development
- Windows Driver Kit (WDK)
- Native C and portable filesystem engines
- OpenZFS architecture and on-disk formats
- ZFS copy-on-write, compression, checksums, mirrors, and snapshots
- .NET 10 / C# and xUnit
- Native interoperability using P/Invoke
- Automated integration testing and filesystem corruption detection

Your mission is to implement a new native Windows ZFS filesystem driver written primarily in C, together with a reusable user-mode C library and comprehensive C# automated tests.

This is an actual software implementation project, not a proof-of-concept description.

Implement functionality incrementally and verify each milestone against genuine ZFS disk images.

Do not claim that incomplete functionality is operational.

---

# 1. Repository layout and reference source

The repository is initialized by the project owner.

Inside the repository, an existing subdirectory is provided:

    OpenZFS/

This directory contains the upstream OpenZFS source code.

Treat `OpenZFS/` as the authoritative reference for ZFS behavior, filesystem structures, algorithms, and supported features.

Before implementing anything:

1. Inspect the entire repository structure.
2. Verify the contents and exact commit of `OpenZFS/`.
3. Inspect the upstream ZFS architecture.
4. Identify reusable ZFS components.
5. Identify Linux-specific code that cannot execute on Windows without adaptation.
6. Analyze compatibility and licensing constraints.
7. Produce an implementation plan.

Do not rewrite established ZFS algorithms without a compelling technical reason.

Do not modify `OpenZFS/` directly unless an explicit task requires a documented change.

Prefer an adapter layer around reusable upstream code.

If necessary, investigate the existing OpenZFS Windows port as an additional reference:

https://github.com/openzfsonwindows/openzfs

The intended result is a new, independently maintained Windows implementation that remains compatible with mainstream OpenZFS pools.

# 2. Required architecture

Implement three major components.

## A. Portable ZFS engine — C

Location:

    src/native/ZfsCore/

Build a portable ZFS engine written in C.

The engine must support:

- Opening ZFS pools
- Parsing vdev labels
- Reading and validating uberblocks
- Interpreting block pointers
- Reading ZFS objects
- Dataset discovery
- Directory traversal
- File reads
- Checksums
- Compression and decompression
- Snapshot discovery and reading
- Pool and dataset modification in later milestones
- Copy-on-write transactions in later milestones
- Mirrored virtual devices in later milestones

The engine must not directly depend on the Windows kernel.

Implement platform abstractions for:

- Block I/O
- Allocation
- Synchronization
- Logging
- Time
- Error handling

Use a well-defined C API with opaque handles.

Compile the shared core into a Windows user-mode DLL and, with appropriate kernel adapters, into the native driver.

## B. Windows native kernel driver — C

Location:

    src/native/ZfsDriver/

Produce:

    ZfsWindows.sys

Implement a real Windows filesystem driver using WDK.

Progressively support:

- Pool discovery
- Volume mount and dismount
- File and directory enumeration
- File reads
- Metadata operations
- File creation and writing
- Flush and synchronization
- Concurrent filesystem operations
- Snapshot-aware filesystem access

The filesystem driver must use correct Windows kernel synchronization, memory-management, I/O, and caching mechanisms.

Do not assume that a filesystem minifilter provides a complete filesystem implementation.

Do not install or load the experimental driver on the developer's primary machine.

## C. User-mode C DLL and .NET test framework

Location:

    src/native/ZfsNativeApi/
    src/managed/Zfs.Interop/
    tests/Zfs.Core.Tests/

Produce:

    ZfsCore.dll

Expose the same filesystem engine to C#.

Use .NET 10 and xUnit.

All core integration tests must be executable on a normal Windows machine without installing the kernel driver.

Example:

    dotnet test

Separate kernel integration tests into a dedicated project requiring an isolated Windows VM.

Examples:

        disk01.raw
        disk02.raw

Each file represents a block device containing genuine ZFS data structures.

Implement:

    IBlockDevice

The native abstraction must support:

- Open
- Close
- Read at offset
- Write at offset
- Flush
- Device size
- Logical sector size
- Physical sector size
- Read-only access
- Exclusive write access

Support both:

1. Raw ZFS vdev image files.
2. Complete disk images containing GPT partitions.

Avoid hardcoded device offsets.

The block-device interface must be usable by both the user-mode DLL and kernel driver.

Write access must initially be allowed only on explicitly designated disposable test images.

Generate workloads similar to scenario A:

- Approximately 4 GiB of logical application data when capacity permits
- Large files
- Small files
- Compressible data
- Incompressible data
- Nested directories

## Mirror read testing

1. Create the mirror using upstream OpenZFS.
2. Populate data.
3. Export the pool.
4. Open both images using the Windows engine.
5. Verify pool configuration.
6. Read all files.
7. Verify hashes.

## Mirror degradation testing

On disposable copies only:

1. Simulate one unavailable mirror member.
2. Reopen the pool with the remaining device.
3. Verify expected degraded read behavior.
4. Validate all accessible files.

## Mirror corruption testing

1. Clone the golden mirror images.
2. Corrupt selected blocks on one member.
3. Verify checksums detect corruption.
4. Verify reads can obtain valid data from the other member.
5. Verify returned file hashes.

## Mirror repair testing

Once repair functionality exists:

1. Simulate a failed member.
2. Replace it with a new blank image.
3. Trigger the supported replacement/resilver workflow.
4. Verify resilver completion.
5. Verify file hashes.
6. Independently validate the pool using upstream OpenZFS.

Do not claim automatic self-healing until actual repair and subsequent validation have been demonstrated.

# 9. Test scenario E — ZFS snapshots

Create:

    TestVolumes/snapshots/disk01.raw

Support snapshot creation, enumeration, reading, rollback, and deletion in separate milestones.

## Snapshot lifecycle

Create initial files:

    /documents/report.txt
    /documents/config.json
    /binary/data.bin

Record hashes.

Create:

    tank/test@snapshot1

Modify the original files.

Create new files.

Delete some original files.

Create:

    tank/test@snapshot2

Modify files again.

Create:

    tank/test@snapshot3

## Required validations

Verify that:

- Current dataset contains the latest data.
- Snapshot1 exposes original file contents.
- Snapshot2 exposes intermediate file contents.
- Snapshot3 exposes its expected contents.
- Deleting a file from the live dataset does not remove it from existing snapshots.
- Modifying a live file does not alter earlier snapshots.
- Snapshot enumeration returns the correct snapshot identifiers.
- Snapshot reads return the expected historical SHA-256 hashes.

## Snapshot rollback

On a disposable pool:

1. Record the latest dataset state.
2. Roll back to a selected snapshot.
3. Verify expected files and hashes.
4. Verify that rollback follows documented ZFS snapshot/dependency semantics.

## Snapshot deletion

Delete selected snapshots using supported ZFS semantics.

Verify:

- Remaining snapshots are readable.
- The live dataset remains consistent.
- Relevant block reference counts and space accounting remain valid.

Snapshot creation and deletion must not be implemented as ordinary full-file copies.

Use genuine ZFS copy-on-write snapshot semantics.

# 13. Critical data-integrity requirements

Data correctness has priority over performance.

For every fixture:

- Maintain independent SHA-256 reference hashes.
- Validate file lengths.
- Validate directory entries.
- Validate pool metadata.
- Detect unsupported feature flags.
- Detect corrupted blocks.
- Detect malformed metadata.
- Prevent out-of-bounds block access.
- Prevent integer overflow.
- Validate physical device bounds.

For read-only tests, calculate image hashes before and after execution.

The image must remain byte-for-byte identical.

For write tests, preserve the original golden image and perform operations on an isolated copy.

Never allow an automated test to modify a real physical disk.

The default mode must be read-only.

Enable image writes only when the test explicitly selects a disposable writable image.

Never silently perform GPT repair, partition initialization, pool upgrades, or disk formatting.

**M7 — Snapshot reading**

**M10 — Windows kernel driver**

Implement and validate the native `.sys` filesystem driver in an isolated Windows VM.

**M11 — Stress testing and performance optimization**

Run large-scale integrity tests, corruption injection, failure scenarios, and performance benchmarks.

# 17. Acceptance criteria

A feature is considered implemented only when:

1. The code builds successfully.
2. The relevant C# tests execute successfully.
3. The tests use real ZFS structures rather than mock data.
4. Expected file contents and SHA-256 hashes match.
5. Read-only images are unchanged.
6. Writable images remain readable by upstream OpenZFS.
7. Error scenarios are handled without undefined behavior.
8. Test reports contain verifiable results.
9. Unsupported functionality is documented accurately.

A successful compile is not sufficient.

A passing mock test is not sufficient.

An image that can be read only by this project's own code is not sufficient proof of upstream compatibility.
